# Обратная связь по PuuNote Sandbox (Разбор бага "167:34")

Анализ скриншота, на котором джоба зависла на **167 минут 34 секунды** на первой модели (Key 1/3), наглядно демонстрирует самую коварную проблему сетевого программирования на клиенте.

## Почему это произошло?

### 1. Бесконечный `fetch` (TCP Half-Open)
Стандартный браузерный `fetch` **не имеет встроенного таймаута**. Если во время выполнения запроса:
* Пользователь закрыл крышку ноутбука (Слип мод)
* Мобильный интернет мигнул при переходе в метро
* Балансировщик Google сбросил соединение, не прислав TCP FIN-пакет...

...то `fetch` будет висеть в состоянии `Pending` **бесконечно**. Часы будут тикать, а Promise никогда не разрешится (ни `resolve`, ни `reject`).

### 2. Слип-мод убил `setTimeout`
Если таймаут для прерывания в главном расширении был написан через `setTimeout(() => controller.abort(), 180000)`, это плохая новость. Во время спящего режима ОС (когда ноутбук уснул) таймеры JavaScript ставятся на паузу. Спустя 3 часа ноутбук проснулся — таймер продолжил тикать с того же места, а `fetch` продолжил висеть.

### 3. Отмена пользователем vs Сетевой таймаут
Еще одна архитектурная ловушка: как отличить, отменил ли пользователь запрос вручную (нажал крестик), или сработал таймаут системы?
Если `controller.abort()` вызывается по таймауту, он генерирует `AbortError`. Если код ловца ошибок (Catch block) не отличает таймаут от ручной отмены, он может либо убить всю джобу (вместо перехода к следующей модели), либо некорректно поймать ошибку и зависнуть.

---

## Как это исправить в продакшене (Рекомендации для разработчика)

### ✅ Использовать нативный `AbortSignal.timeout()`
Современные браузеры поддерживают нативный таймаут прямо в сигнале. Он более устойчив к зависаниям:
```javascript
const userController = new AbortController(); // Для ручной отмены (крестика)

// Комбинируем ручную отмену и железный таймаут на 3 минуты
const timeoutSignal = AbortSignal.timeout(3 * 60 * 1000); 
const combinedSignal = AbortSignal.any([userController.signal, timeoutSignal]);

try {
  const response = await fetch(url, { signal: combinedSignal });
} catch (err) {
  if (err.name === 'TimeoutError') {
    // Это именно ТАЙМАУТ! Спокойно пишем в лог "Таймаут модели X" 
    // и логика цикла должна пойти на следующую модель `continue`.
  } else if (err.name === 'AbortError') {
    // Это ручная отмена пользователем. Прерываем ВСЮ цепочку.
    throw new Error('Отменено пользователем');
  }
}
```

### ✅ Пересмотреть логику "Skip" (Кнопка ⏭️)
На скриншоте видна отличная кнопка "Пропустить" (Forward). Это спасение для UX! 
Она должна принудительно выбрасывать кастомную ошибку (например, `UserSkipError`), чтобы текущий `fetch` обрывался, а цикл `catch` ловил её и ИГНОРИРОВАЛ `break`, делая принудительный переход на следующий ключ/модель. 

**Итог:** Зависание на 167 минут — это классика фронтенд-разработки. Механизм фолбэка должен быть безжалостным. Если через `N` секунд модель не отдала хотя бы один байт (First Byte) — немедлено обрывать коннект (TimeoutError) и стрелять в следующую модель.
